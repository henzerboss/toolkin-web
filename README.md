# toolkin.app

Бэкенд и лендинг Toolkin. Next.js 15 · React 19 · Prisma · Postgres.

Здесь живёт всё, что нельзя доверить устройству: ключ модели, генерация спек с
циклом починки и баланс кредитов. Приложение (Expo) знает только свой анонимный
`appUserId` из RevenueCat.

## Запуск

```bash
npm install
cp .env.example .env        # заполнить DATABASE_URL и TOOLKIN_GEMINI_API_KEY
npx prisma migrate dev --name init
npm run dev
```

Проверка ядра без базы и без сети:

```bash
npx tsx test-api.ts
```

Тест гоняет валидатор на трёх эталонных спеках и на заведомо сломанной, плюс
проверяет разбор пакетов кредитов. Он не поднимает Postgres — вся ценовая логика
вынесена в `src/lib/pricing.ts` именно ради этого.

## Роуты

| Метод | Путь | Назначение | Цена |
|---|---|---|---|
| POST | `/api/generate` | промпт → спека утилиты | 5 кредитов |
| POST | `/api/refine` | спека + правка → новая версия | 2 кредита |
| POST | `/api/ask` | экшен `llm.ask` внутри утилиты | 1 кредит |
| GET | `/api/credits` | баланс, лимиты, актуальные цены | — |
| GET | `/api/app-version` | проверка обновления в сторе | — |
| POST | `/api/webhooks/revenuecat` | начисление кредитов по покупкам | — |

Все API-роуты: `runtime = 'nodejs'`, CORS с `OPTIONS`, заголовок `X-Client-Token`,
лимит по IP, `Cache-Control: no-store` через `next.config.ts`.

Идентификация — заголовок `X-App-User-Id`. Регистрации нет: этого требует App
Store 5.1.1(v), и это же снимает необходимость хранить персональные данные.

## Как устроена генерация

```
запрос → планирование (responseSchema, enum'ы из манифеста)
       → коррекция плана кодом (игра ⇒ песочница, камера+история ⇒ галерея)
       → сборка промпта только из нужных разделов
       → Gemini (JSON-режим) → validateSpec → ошибки → починка → … (до 2 повторов)
       → списание кредитов → спека клиенту
```

**Два этапа вместо одного.** Полный промпт вырос до двенадцати тысяч знаков, и
правила из его середины модель теряла: игры собирались из кнопок, числа тащились
из свободного текста. Дублирование правил в конце помогало частично — это была
подпорка.

План решает то же самое архитектурно. Он маленький и целиком описывается схемой,
поэтому ограниченное декодирование гарантирует: несуществующего компонента или
возможности в нём не будет. А главное — план настолько прост, что его ошибки
исправляются **кодом**, а не уговорами. «Игра значит песочница» перестало быть
просьбой к модели и стало правилом в `_plan.ts`.

Дальше промпт второго этапа собирается только из относящихся к делу разделов:
для игры это 7 300 знаков вместо 12 000, для фото-утилиты 9 500. Короткий промпт
модель выполняет точнее.

Схема применяется только к плану, и это осознанно. В самой спеке половина полей —
словари с произвольными ключами (`state`, `derived`, `fields`, `values`), а Gemini
такие структуры схемой не описывает. Схема там, где она работает; промпт там, где
не работает схема.

**Модели по задачам.** `TOOLKIN_MODELS_PLAN`, `_GENERATE`, `_REFINE`, `_ASK`,
`_TRANSLATE` переопределяют общий каскад. Генерация случается редко и требовательна
— ей старшая модель. Ответы внутри утилит массовые и простые, а задержка там
заметна пользователю напрямую — им быстрая. Планирование и перевод промпта для
картинки настолько узкие, что старшая модель только тратит время.

Манифест DSL (`src/lib/dsl.ts`) — **один файл на сайт и на приложение**. Из него
собирается и описание компонентов для промпта, и правила валидации. Приложение в
dev-режиме проверяет, что каждый компонент манифеста зарегистрирован в рантайме,
поэтому промпт не может пообещать блок, которого нет на устройстве.

**Промпт и все сообщения валидатора написаны по-английски.** Дело не в экономии
токенов — она здесь копеечная. Дело в примерах: модель копирует из них не только
структуру, но и язык подписей, и русские образцы перетягивали вывод на русский
даже при явной инструкции писать на языке устройства. Язык интерфейса создаваемой
утилиты задаётся отдельной строкой и от языка промпта не зависит.

Ошибки валидатора написаны как инструкции для модели, а не для логов:

```
ui.children[1] (Slider): bind="nope" is not declared in state. Available: bill, tipPct, people
ui.children[2].onPress[0]: action "clipboard.set" requires capability "clipboard" —
  add it to capabilities or the step will not run
```

Цикл починки поднимает долю успешных генераций примерно с 80% до 97% ценой одного
лишнего вызова. Он на сервере, чтобы пользователь не платил круговым рейсом.

## Качество генерации

```bash
TOOLKIN_GEMINI_API_KEY=... npm run eval
TOOLKIN_GEMINI_API_KEY=... npx tsx scripts/eval.ts --thinking medium --runs 2
```

Прогоняет 20 запросов через настоящий конвейер и печатает три числа: долю спек,
прошедших валидатор **с первой попытки**, число невыполненных ожиданий (игра без
песочницы, фото-утилита без камеры) и среднее время. Плюс гистограмму причин
починки — она показывает, какое правило промпта чинить следующим.

Итоговая доля успеха после починки для сравнения бесполезна: она почти всегда
близка к единице и прячет то, во сколько лишних вызовов и секунд обходится
каждая генерация. Набор намеренно смещён в сторону того, что ломалось — игры,
фото, числа от модели; ровные калькуляторы завышали бы метрику.

Любую правку промпта, модели или уровня размышления имеет смысл сравнивать
этими числами до и после. Иначе получается то, чем мы занимались до сих пор:
правка по одному скриншоту без понимания, стало лучше или хуже.

### Параметры модели

`thinkingLevel` задаётся отдельно для генерации (`high`), правки (`medium`) и
ответов внутри утилит (`low`). Генерация — это планирование: выбор между
песочницей и декларативной сборкой, между `fields` и свободным текстом. Ответ
внутри утилиты планирования не требует, зато напрямую добавляет секунды ожидания.

**Температуры в конфиге нет намеренно.** Gemini 3 её игнорирует вместе с topK и
topP, и видимая, но не работающая ручка хуже отсутствующей.

## Кредиты

Списание происходит **после** успешного ответа модели: неудачная генерация не
стоит ничего. Бесплатные генерации тратятся раньше купленных кредитов — иначе
человек обнаружит, что заплаченное ушло, пока бесплатное лежало нетронутым.

Начисление идёт вебхуком RevenueCat. Идемпотентность обеспечивает уникальный
`eventId` в таблице `Ledger`: RevenueCat повторяет доставку любого события, на
которое получил 5xx, и без этого одна покупка начислилась бы дважды.

Секрет вебхука сверяется через `timingSafeEqual`. Обычное сравнение строк выходит
на первом несовпавшем байте, и по времени ответа секрет подбирается посимвольно.

## Деплой

Разворачивается на своём VPS: Nginx через CloudPanel, процесс под PM2, Postgres
рядом. Пошагово — в `DEPLOY.md`, включая типовые ошибки с сертификатом и портом.

Один домен обслуживает и лендинг, и API: `https://toolkin.app/api/...`. Отдельный
поддомен `api.` на своём сервере только добавляет сертификат и vhost без пользы,
поэтому в приложении `EXPO_PUBLIC_API_BASE=https://toolkin.app/api`.

Вебхук RevenueCat — `https://toolkin.app/api/webhooks/revenuecat`, секрет в
`TOOLKIN_REVENUECAT_WEBHOOK_SECRET`.

Обновление всегда в таком порядке, иначе новый код успеет поработать на старой
схеме:

```bash
npm install && npx prisma migrate deploy && npm run build && pm2 restart toolkin
```

## Страницы

`/`, `/privacy`, `/support` — статические. Политика и поддержка нужны не для
маркетинга: без рабочих ссылок на них ревью в обоих сторах не проходит. Тексты
в `src/app/privacy` и `src/app/support` — черновики, сверьте их с юристом и с
карточкой App Privacy перед подачей.
