# toolkin.app

Бэкенд и лендинг Toolkin. Next.js 15 · React 19 · Prisma · Postgres.

Здесь живёт всё, что нельзя доверить устройству: ключ модели, генерация спек с
циклом починки и баланс кредитов. Приложение (Expo) знает только свой анонимный
`appUserId` из RevenueCat.

## Запуск

```bash
npm install
cp .env.example .env        # заполнить DATABASE_URL и TOOLKIN_GEMINI_API_KEY
npx prisma migrate dev
npm run dev
```

Проверка ядра без базы и без сети:

```bash
npx tsx test-api.ts
```

Тест гоняет валидатор на трёх эталонных спеках и на заведомо сломанной, плюс
проверяет разбор пакетов кредитов. Он не поднимает Postgres — вся ценовая логика
вынесена в `src/lib/pricing.ts` именно ради этого.

## Роуты

| Метод | Путь | Назначение | Цена |
|---|---|---|---|
| POST | `/api/plan` | запрос → Product Plan + подписанный `planToken` | — |
| POST | `/api/generate` | подтверждённый plan → Spec v2 | 5 кредитов |
| POST | `/api/refine` | спека + правка → новая версия | 2 кредита |
| POST | `/api/ask` | экшен `llm.ask` внутри утилиты | 1 кредит |
| GET | `/api/credits` | баланс, лимиты, актуальные цены | — |
| GET | `/api/app-version` | проверка обновления в сторе | — |
| POST | `/api/webhooks/revenuecat` | начисление кредитов по покупкам | — |

Все API-роуты: `runtime = 'nodejs'`, CORS с `OPTIONS`, заголовок `X-Client-Token`,
лимит по IP, `Cache-Control: no-store` через `next.config.ts`.

Идентификация — заголовок `X-App-User-Id`. Регистрации нет: этого требует App
Store 5.1.1(v), и это же снимает необходимость хранить персональные данные.

## Как устроена генерация v2

```
request
  → Product Plan (features + acceptance criteria + screens + component gaps)
  → HMAC-signed planToken
  → user feature selection / custom features
  → exact immutable Product Plan
  → UX/AppSpec v2 generation
  → validateSpec
  → autofix
  → behavioral smokeTest (fresh + filled)
  → checkFeatures(featureEvidence + exact requirements)
  → repair loop
  → credits charge
  → client
```

**План теперь является контрактом, а не подсказкой.** `/api/plan` возвращает
Product Plan и подписанный `planToken`. `/api/generate` проверяет подпись,
expiration, locale и hash исходного запроса и строит приложение именно из того
плана, который видел пользователь. Второй вызов planner больше не может
незаметно поменять feature IDs или информационную архитектуру. Старый клиент без
token остаётся совместим и использует legacy planning path.

Для production задайте отдельный `TOOLKIN_PLAN_SECRET`. Token не содержит
секретов, живёт ограниченное время и защищает server-side контракт от подмены.
Cache key включает fingerprint фактически согласованного плана и выбранных
фичей, поэтому спека от другого плана не может попасть в ответ из кэша.

**Product Plan описывает результат, а не только компоненты.** Для каждой feature
есть acceptance criteria и точные механические requirements. План также
предлагает 1–4 экрана и component gaps. Генератор сначала проектирует UX под
задачу, а затем решает gap в порядке `REUSE → COMPOSE → EXTEND`; произвольный
React Native не генерируется.

Spec v2 поддерживает `single`/`stack`/`tabs`, named collections, `Repeat`,
app-local declarative composite components, design tokens и `featureEvidence`.
Это снимает старый потолок «один экран из 4–8 блоков»: специфичные элементы вроде
`ExpenseCard`, `WorkoutSetRow` или `HabitWeekCell` собираются из безопасных core
primitives внутри самой спеки и проходят ту же валидацию.

**Custom feature — полноценное обещание.** Пользовательский пункт получает
acceptance criterion и обязан иметь concrete `featureEvidence`; он больше не
исключается из проверки. `checkFeatures` не считает `DateField` календарём,
`ProgressRing` графиком или `image.generate` эквивалентом `llm.ask`: evidence
должен ссылаться на реально существующие components/actions/capabilities.

**Validator проверяет исполнимость контракта.** Помимо формы JSON он проверяет
screen targets, navigation mode, component cycles, props/bind, record schemas,
collection names, action arguments и capabilities. `collections.default`
зарезервирована для legacy top-level `records`. Sandbox не получает обходной
путь к host API: камера, LLM, image generation и notifications требуют тех же
capabilities, что обычные actions; внешняя сеть и скрипты запрещены.

**Smoke-test моделирует поведение, а не наличие виджетов.** Он выполняется на
fresh и filled state, разворачивает composite components/`Repeat`, применяет
локальный record context, выполняет CRUD/navigation и строго соблюдает `when`.
Так сервер ловит класс ошибок «валидация зелёная, но кнопка на устройстве ничего
не делает». Следующий возможный слой — screenshot-based visual QA; он не заменяет
behavioral checks.

**Автопочинка** остаётся только для однозначных синтаксических привычек модели
(`Math.*`, `state.*`, `.length`, `===`, `Date.now()` и т.п.). Семантические
изменения делает repair loop, получая конкретные validation/behavior/feature
issues.

Манифест DSL (`src/lib/dsl.ts`) синхронизирован с мобильным
`src/domain/spec/dsl.ts`; типы Spec v2 синхронизированы аналогично. Новые server
capabilities нельзя выпускать отдельно от runtime, если старый клиент их не
понимает, поэтому оба проекта проверяются как один контракт.

**Модели по задачам.** `TOOLKIN_MODELS_PLAN`, `_GENERATE`, `_REFINE`, `_ASK`,
`_TRANSLATE` по-прежнему переопределяют общий каскад. Планирование, генерация и
runtime-ответы имеют разные требования к latency/quality, поэтому разделение
сохраняется.

## Расходы на модель

Три механизма, в порядке вклада.

**Кэш спек.** Одинаковый запрос не оплачивается дважды: спека детерминирована
относительно запроса, языка и версии конвейера. Примеры-затравки на экране
создания одинаковы у всех пользователей, поэтому первые генерации новичков почти
всегда приходят из кэша — бесплатно и мгновенно. Ключ нормализует регистр,
пробелы и хвостовую пунктуацию.

Версия конвейера вычисляется из отпечатка DSL-манифеста **и канонических
probe-промптов**. Поэтому правки компонентов, экшенов, функций, фильтров или
генераторного prompt автоматически инвалидируют кэш — улучшения не могут
месяцами скрываться за старой сгенерированной спекой.

Руками меняется только `CACHE_EPOCH` в `src/lib/specCacheKey.ts`, когда меняется
**validator/autofix-семантика**, не отражённая в DSL или prompt. Спека, валидная
вчера, после такого ужесточения тоже не должна возвращаться из старого кэша.

**Короткий промпт по плану.** Для игры второй этап получает 7 900 знаков вместо
12 000. Плюс дешёвая модель на планирование и на ответы внутри утилит.

**Учёт расхода.** Фактические токены каждой генерации пишутся в `Ledger.meta`,
включая токены размышления — при `thinkingLevel=high` они составляют заметную
долю, и без отдельного учёта счёт выглядит необъяснимым.

```sql
select
  (meta::json->>'kind') as kind,
  count(*),
  avg((meta::json->'tokens'->>'input')::int)   as in_avg,
  avg((meta::json->'tokens'->>'output')::int)  as out_avg,
  avg((meta::json->'tokens'->>'thoughts')::int) as think_avg
from "Ledger" where reason = 'generate' group by 1 order by 2 desc;
```

## Качество генерации

```bash
npm run eval                                  # на сервере, ключ берётся из .env
npm run eval -- --thinking medium --runs 2    # сравнить настройки

TOOLKIN_GEMINI_API_KEY=... npm run eval       # локально, если .env нет
```

Прогон и тесты запускаются через `tsx`, он в devDependencies. Если `npm install`
выполнялся с `NODE_ENV=production`, dev-зависимости пропущены — поставьте их
явно: `npm install --include=dev`.

Прогоняет 20 запросов через настоящий конвейер и печатает три числа: долю спек,
прошедших валидатор **с первой попытки**, число невыполненных ожиданий (игра без
песочницы, фото-утилита без камеры) и среднее время. Плюс гистограмму причин
починки — она показывает, какое правило промпта чинить следующим.

Итоговая доля успеха после починки для сравнения бесполезна: она почти всегда
близка к единице и прячет то, во сколько лишних вызовов и секунд обходится
каждая генерация. Набор намеренно смещён в сторону того, что ломалось — игры,
фото, числа от модели; ровные калькуляторы завышали бы метрику.

Любую правку промпта, модели или уровня размышления имеет смысл сравнивать
этими числами до и после. Иначе получается то, чем мы занимались до сих пор:
правка по одному скриншоту без понимания, стало лучше или хуже.

### Параметры модели

`thinkingLevel` задаётся отдельно для генерации (`high`), правки (`medium`) и
ответов внутри утилит (`low`). Генерация — это планирование: выбор между
песочницей и декларативной сборкой, между `fields` и свободным текстом. Ответ
внутри утилиты планирования не требует, зато напрямую добавляет секунды ожидания.

**Температуры в конфиге нет намеренно.** Gemini 3 её игнорирует вместе с topK и
topP, и видимая, но не работающая ручка хуже отсутствующей.

## Кредиты

Списание происходит **после** успешного ответа модели: неудачная генерация не
стоит ничего. Бесплатные генерации тратятся раньше купленных кредитов — иначе
человек обнаружит, что заплаченное ушло, пока бесплатное лежало нетронутым.

Начисление идёт вебхуком RevenueCat. Идемпотентность обеспечивает уникальный
`eventId` в таблице `Ledger`: RevenueCat повторяет доставку любого события, на
которое получил 5xx, и без этого одна покупка начислилась бы дважды.

Секрет вебхука сверяется через `timingSafeEqual`. Обычное сравнение строк выходит
на первом несовпавшем байте, и по времени ответа секрет подбирается посимвольно.

## Деплой

Разворачивается на своём VPS: Nginx через CloudPanel, процесс под PM2, Postgres
рядом. Пошагово — в `DEPLOY.md`, включая типовые ошибки с сертификатом и портом.

Один домен обслуживает и лендинг, и API: `https://toolkin.app/api/...`. Отдельный
поддомен `api.` на своём сервере только добавляет сертификат и vhost без пользы,
поэтому в приложении `EXPO_PUBLIC_API_BASE=https://toolkin.app/api`.

Вебхук RevenueCat — `https://toolkin.app/api/webhooks/revenuecat`, секрет в
`TOOLKIN_REVENUECAT_WEBHOOK_SECRET`.

Обновление всегда в таком порядке, иначе новый код успеет поработать на старой
схеме:

```bash
npm install && npx prisma migrate deploy && npm run build && pm2 restart toolkin
```

## Страницы

в `src/app/privacy` и `src/app/support` — черновики, сверьте их с юристом и с
карточкой App Privacy перед подачей.
